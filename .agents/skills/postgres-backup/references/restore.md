# Restore a PostgreSQL backup

1. Identify the bundle, source timestamp, desired restore target and downtime before any live change. Use only trusted dumps. Run `python <path-to-backup.py> --verify <bundle>` on the selected local or external copy. Inspect the archive table of contents with `pg_restore --list`. Verify that the target ships compatible builds of each source extension, including `postgis`, `postgis_raster`, `postgis_topology`, `h3`, and `h3_postgis`, and use a `pg_restore` version that supports the archive and target.
2. Test in a separate database on a compatible server or an isolated Compose instance with its own empty bind mount and an unused port. The template initializes extensions in its configured database, so create an additional empty database from `template0` for the restore. Match source encoding and locale when needed. Inventory and provision required roles, memberships, and tablespaces first to preserve ownership and grants. In the original cluster those globals ordinarily already exist. For a fresh cluster, review `globals.sql` privately and reconcile the bootstrap role and mapped tablespace paths explicitly. A fresh instance with a distinct bootstrap role avoids duplicate `CREATE ROLE` statements. Apply reviewed globals with `psql -X -v ON_ERROR_STOP=1` and confirm application credentials. Do not suppress failures or discard ownership and ACLs to make a restore pass.
3. Copy the archive into the target container using `docker compose cp <archive> db:<private-target-path>`, using a unique path in a private directory. From the **target** Compose project run `docker compose exec -T db pg_restore --username <admin> --dbname <empty-database> --exit-on-error --single-transaction <private-target-path>`. Use private binary file handles for streaming across Windows shells. For a whole-database restore that preserves the original database settings and grants, `pg_restore --create --exit-on-error --dbname <maintenance-db>` creates the original name from the archive. Use that form only in an isolated cluster where the original name is available. It performs database creation outside the restore transaction. Remove the temporary archive after verification.
4. Compare the inventory, key table counts, large objects, owners and grants, schemas, and extension versions with the source or the recorded backup baseline. Exercise representative geometry, raster, topology and H3 queries and an application connection. Record discrepancies and stop before cutover if they remain unresolved. `pg_restore --list` and a checksum alone never establish recoverability.
5. For live recovery, preserve the previous cluster and route clients to the verified restore only with the administrator's authorization for the target and recovery point. Explain which writes after the backup time would be missing. Keep the backup and prior data until the administrator confirms there is no remaining recovery need.

# Execute a PostgreSQL upgrade

## Inventory and rehearse

1. Record the running image ID, PostgreSQL version, Docker context, effective bind source and `PGDATA`, and required settings. Retain the exact old runnable image and Compose configuration privately. Inspect databases, roles, tablespaces, encodings and collations, installed extension versions and available upgrade paths, plus replication and scheduled jobs when present. A `geodata` dump and globals do not cover other databases, server configuration, replication, or external tablespace mounts. Add any required assets to the plan. Treat an unsupported dependency as a blocker.
2. Build the candidate from an explicit stable `postgis/postgis` tag and verified digest. Use the `postgresql-<major>-h3` package for its PostgreSQL major. Prove the expected PostgreSQL, PostGIS and H3 versions in the resulting image and retain its exact image ID. Check the target's mount layout from its image. Both the existing template and PostgreSQL 18+ images mount `/var/lib/postgresql`, with version-specific `PGDATA` below it. A new path with an empty, initialized database is not a migration.
3. Create a backup and restore it in an isolated Compose project with a separate bind directory, unique project name and no published port, or a distinct loopback-only port when required. Follow the [restore procedure](../../postgres-backup/references/restore.md), including roles, ownership and grants. Verify all installed extensions and their actual libraries plus representative geometry, raster, topology and H3 behavior. Compare critical data and application queries with the source. Rehearse cutover and rollback, and record measured downtime and validation results.
4. Use a fresh-cluster logical dump and restore for a major upgrade by default. Initialize the candidate with a distinct bootstrap role and use a maintenance database whose name does not conflict with an archived database. Use `pg_restore --create` only where the original database name is free. A fresh cluster already has a `postgres` database. Restore user objects from a source `postgres` database into that database and review its database-level metadata separately. Choose `pg_upgrade` only when the exact target manuals, available binaries, extension compatibility and rehearsal justify it. Use a copy of the source cluster and keep the rollback cluster independent. If a PostGIS extension requires its own hard upgrade, rehearse the PostGIS-documented procedure with the full dump and verify raster, topology, `spatial_ref_sys`, and user-owned objects.
5. A minor upgrade on the same major can reuse physical data if its release notes allow it. Prefer a storage snapshot or stopped, independent copy that preserves permissions and includes external tablespaces. Never copy a running physical data directory as a backup with an ordinary filesystem copy. Apply extension and collation actions only when the relevant release notes and rehearsal require them. Check for required reindexing or statistics refresh.

## Cut over with rollback available

1. Use the approved target and maintenance window. Stop all application writers, suspend scheduled jobs including automatic backups, drain client sessions, and prevent reconnection before the final recovery point. Verify the write pause and freeze role and tablespace changes. An earlier rehearsal backup cannot be the final migration source while writes are still possible.
2. While writes are paused, take and verify a final backup and preserve the independent rollback cluster. For a major upgrade, restore this final backup into a **fresh** candidate. For a minor physical upgrade, snapshot or copy the stopped source for the target and keep the original unchanged. Reapply the rehearsed deployment settings and the measured checks against the final candidate. Preserve database-level settings, privileges and credentials as well as data. Halt if archives fail to restore, extensions or dependent functions are missing, counts or key invariants differ, or required clients cannot connect.
3. Stop the old listener, start the exact tested candidate on `5432` and verify its bind mount and runtime image ID. Keep clients blocked during the pre-write checks, including applications that reconnect automatically. If a check fails before writes resume, bring back the retained old image and unchanged old data directory on the original endpoint. After the new server accepts writes, switching back would discard writes unless they are captured and reconciled. Pause writes again and coordinate recovery before such a rollback.
4. Update repository defaults for the chosen version if the administrator is updating the template as well as the deployment. Review `docker/Dockerfile`, `README.md`, the expected PostgreSQL major in `tests/smoke.sql`, init scripts and the volume path. Confirm the backup job still targets the intended Compose project and resume suspended jobs. Report the running versions, checked functionality, backup location and rollback state. Retain old data, image and backups according to the administrator's retention policy.
